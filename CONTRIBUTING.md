# Как внести вклад в руководство

Спасибо, что помогаете улучшать руководство по стилю «Таскбука». Здесь описано, как предложить изменение, оформить коммиты, пройти ревью и собрать сайт локально.

## Как предложить изменение

1. Если изменение крупное или спорное, сначала создайте issue и опишите проблему: какое правило нужно добавить или изменить и почему.
1. Создайте ветку от `main`. Имя ветки начинается с типа изменения: `feat/accessibility`, `fix/dash-rule`, `docs/contributing`.
1. Внесите изменения. Новые правила оформляйте так же, как существующие: правило, пояснение, примеры «Неправильно» и «Правильно».
1. Запустите линтеры и локальную сборку. Как это сделать, описано ниже в разделе [Локальная сборка](#локальная-сборка).
1. Сделайте коммит по правилам из раздела [Коммиты](#коммиты).
1. Отправьте ветку в репозиторий и создайте pull request в `main`.

Прямые коммиты в `main` не допускаются: все изменения проходят через pull request.

## Коммиты

Сообщения коммитов оформляются по спецификации [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>(<область>): <описание>
```

| Тип | Когда использовать |
| --- | --- |
| `feat` | Новое правило или новый раздел руководства |
| `fix` | Исправление ошибки в правиле, примере или настройках |
| `docs` | Изменения в README, CONTRIBUTING и других служебных файлах |
| `style` | Форматирование без изменения смысла: пробелы, переносы |
| `refactor` | Перенос и переименование разделов без изменения правил |
| `ci` | Изменения в GitHub Actions |
| `chore` | Зависимости и прочие служебные изменения |

Правила для сообщения:

- область — раздел руководства или компонент: `tone`, `terms`, `lint`, `nav`;
- описание пишется на русском языке, со строчной буквы, без точки в конце;
- описание отвечает на вопрос «что сделано» и начинается с глагола: «добавить», «исправить», «обновить»;
- длина первой строки — не больше 72 символов.

Примеры:

```text
feat(accessibility): добавить раздел о доступности текста
fix(lint): исправить правило Vale для тире
docs: описать процесс ревью в CONTRIBUTING
```

## Процесс ревью

1. Создайте pull request и заполните описание: что изменилось и зачем. Если правило нарушается намеренно, объясните почему.
1. Дождитесь, пока пройдёт проверка **Docs** в GitHub Actions: линтинг и сборка сайта. Pull request с ошибками линтинга не рассматривается.
1. Назначьте ревьюера. Нужно одно одобрение от участника, который не был автором изменений.
1. Ревьюер проверяет:
    - соответствует ли изменение остальным правилам руководства;
    - есть ли у правила примеры;
    - понятна ли формулировка тому, кто видит правило впервые.
1. Ревьюер оставляет комментарии к строкам и отмечает тип комментария в начале: **Замечание** — нужно исправить, **Предложение** — можно улучшить, **Вопрос** — нужно пояснить.
1. Автор отвечает на каждый комментарий, вносит правки отдельным коммитом и отмечает обсуждение как решённое.
1. После одобрения автор выполняет merge в `main`. Сайт обновится автоматически через несколько минут.

## Локальная сборка

Нужны Python 3.10 или новее и Node.js 20 или новее.

1. Установите зависимости:

    ```bash
    python3 -m venv .venv
    source .venv/bin/activate
    pip install -r requirements.txt vale==3.22.0.0
    ```

1. Запустите локальный сервер:

    ```bash
    mkdocs serve
    ```

    Сайт откроется по адресу <http://127.0.0.1:8000/>. Страницы обновляются при сохранении файлов.

1. Перед коммитом запустите проверки:

    ```bash
    npx markdownlint-cli2
    vale docs/examples
    mkdocs build --strict
    ```

    Все три команды должны завершиться без ошибок.

## Как добавить новый раздел

1. Создайте файл `.md` в подходящей папке внутри `docs/`. Имя файла — латиницей, строчными буквами, через дефис: `docs/style/accessibility.md`.
1. Начните файл с заголовка первого уровня и вводного абзаца. Структура раздела описана в правиле [Структура документа и заголовки](docs/formatting/structure.md).
1. Добавьте раздел в навигацию в `mkdocs.yml`, в блок `nav`:

    ```yaml
    nav:
      - Стиль изложения:
          - Доступность текста: style/accessibility.md
    ```

1. Если в разделе появились новые термины, добавьте их в `docs/glossary.md`.
1. Если правило можно проверить автоматически, добавьте правило Vale в `styles/Taskbook/`.
1. Проверьте раздел локально и создайте pull request.
